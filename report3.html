Report 3: Simple Malware in C

Yll Morina

02/05/2026

This report documents a small educational exercise that demonstrates a common Windows persistence mechanism: user-level startup via the Run registry key. The goal was not to build real malware, but to understand the concept, the WinAPI calls involved, and how defenders can detect this behavior.

1. Scope and Safety

This exercise was performed as a controlled classroom-style demo to understand how persistence works on Windows. I ran it only inside my isolated Windows 11 virtual machine environment. The program’s behavior is intentionally simple and observable: it proves execution by showing a message box at logon, and it stores a startup entry under the current user context (no admin privileges required).

I treated this as a defensive learning task. That means I focused on: (1) what the program changes on the system, (2) how Windows triggers it, and (3) how to detect or validate the persistence from a defender perspective.

2. Lab Environment

I used my Windows 11 VM as the “victim” machine. I kept the environment isolated because persistence techniques are the exact same mechanisms used by real malware, and I wanted zero risk of affecting my host system.

In practice, this means the test should happen in a VM with snapshots enabled. If something goes wrong, reverting restores the system back to a known clean state without relying on manual cleanup.

3. Goal of the Program

The program does two things:

  • Shows a visible pop-up to prove it executed (a MessageBox).
  • Creates a user-level startup entry so the program runs automatically after login.

The important part for learning is not the pop-up itself, but the persistence step: writing a startup value so Windows loads the program again in the future.

4. Program Design (High-Level)

Since I am not a C expert, I approached this by first learning the basics of C syntax and then mapping the Windows behavior to specific WinAPI calls. My program logic is straightforward:

  1. Get the full path of the executable currently running.
  2. Open the user’s Run key with permission to set a value.
  3. Write the executable path as a string value.
  4. Close the registry handle cleanly.
  5. Display a message box so I can visually confirm execution.

The reason I used a “current user” persistence location is that it demonstrates a realistic technique without requiring administrative privileges. That constraint matters because many real-world persistence methods try to stay in user-land to avoid UAC prompts or elevated permissions.

5. API Summary and Why Each Matters

These are the core APIs used by the program and the role each one plays: 

GetModuleFileNameA  -> obtains the full path of the running executable
RegOpenKeyExA       -> opens the user’s Run key with write access
RegSetValueExA      -> writes a REG_SZ string value that points to the executable path
RegCloseKey         -> closes the registry handle (avoids resource leaks)
MessageBoxA         -> shows a visible popup as proof the program executed

The important security concept is that registry write APIs are often monitored by EDR solutions, because they are a common way malware establishes persistence. Even if the program is “benign,” the behavior is similar to what defenders look for.

6. What I Did in the Windows 11 VM (Verification Flow)

I kept my testing process very simple and focused on verification:

  • I compiled the program inside the VM using a standard Windows C toolchain. The reason I compiled inside the VM is to keep the entire workflow contained and reproducible.
  • I executed the compiled binary once to confirm it runs without errors and to confirm it can locate its own path.
  • I validated that the startup value exists after execution by checking the Run key entry from the system’s built-in tools (registry viewer / command-line query). I did this step because persistence is not “real” unless the system state actually changed.
  • Finally, I logged out and logged back in (or rebooted) to test the trigger condition. The expected result is seeing the same message box again after login, which confirms the program launched automatically.

For my report evidence, the most important screenshots are:

  • The program’s first execution (showing the message box).
  • The registry entry visible in the Run key after it is created.
  • The message box appearing again after login (proving persistence actually triggered).

7. Why the Run Key Works

The Run key works because Windows processes specific startup locations during user logon. The key idea is simple: the system reads a list of configured programs and launches them automatically when the user signs in.

Using the current user context is also meaningful:

  • It typically does not require administrative permissions.
  • It is easy for an attacker to set, which is why defenders routinely monitor it.
  • It is reliable across reboots and logon sessions unless removed.

8. Detection and Defensive View

From a defender perspective, this technique is not “advanced,” but it is still very common because it is easy and effective. There are a few straightforward ways to detect or investigate it:

  • Autoruns (Sysinternals): quickly lists startup persistence locations in one place.
  • Process Monitor (Procmon): can reveal registry write activity if you capture the event.
  • EDR / AV telemetry: often flags unsigned binaries writing to common startup keys.
  • Forensics / baseline comparison: checking Run key entries against a known-good baseline.

What matters is the behavior: a binary writing itself into an auto-start location. Even a simple demo program can look suspicious if it behaves like persistence-focused malware.

9. Cleanup

After testing, I removed the startup entry so the program would not run again. I also removed the compiled binary from the VM. In a classroom lab, cleanup matters because persistence exercises can quickly become confusing if old entries remain and multiple test binaries start executing at login.

The cleanest method in a VM environment is to revert to a snapshot taken before the persistence step. That returns the registry and filesystem to a known clean state in one action.

10. Conclusion

This exercise helped me understand Windows persistence in a concrete way: not as an abstract “malware trick,” but as a set of normal operating system behaviors that can be abused. By mapping the technique to specific WinAPI calls and then verifying the system changes, I learned what persistence looks like both from an attacker’s view (how it is established) and a defender’s view (how it is validated and detected).
